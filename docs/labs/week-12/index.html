## API and backend requirements

- Use Node.js 22.13 or newer with the API dependencies from `api/package-lock.json`.
- A local API normally listens on `http://localhost:3001`; the frontend development server uses `http://localhost:5173`.
- The frontend reads `VITE_API_BASE_URL`; its default is `http://localhost:3001`. A public deployment needs the HTTPS URL of a running backend and a matching `CORS_ORIGIN` for the frontend origin.
- The API needs the SQLite schema at `api/data/schema.sql` and a writable database location selected by `DB_FILE`. `DB_FILE=:memory:` is suitable for disposable verification. Persistent deployment needs a durable database location or the separately configured remote database supported by the source.
- `/api/health` reports service and database connectivity. CRUD operations use `/api/requests`; user endpoints use `/api/users`.
- For production on one backend origin, build the frontend with `VITE_API_BASE_URL` set to an empty string so it requests `/api/...`, then run the API with `NODE_ENV=production`. Hosting a static build on Pages alone does not supply these endpoints.

## BUG #0 · รายละเอียด 10 ตัวอักษรพอดี ถูกปฏิเสธ (เจอเองจาก unit test)

- **อาการ:** ส่งคำร้องที่รายละเอียดยาว 10 ตัวอักษรพอดี (ตรงตามกฎ "อย่างน้อย 10") แต่ระบบปฏิเสธ บอกว่า "รายละเอียดต้องมีอย่างน้อย 10 ตัวอักษร" — ไม่มีผู้ใช้แจ้ง เจอเองตอนเขียน unit test ค่าขอบ
- **วิธีทำซ้ำ:** เขียน unit test ใน `api/tests/unit/requestValidator.test.js` เรียก `validateRequestInput({ ...valid, details: '1234567890' })` (10 ตัวอักษรพอดี) แล้วคาดหวัง error ว่าง → test fail
- **เครื่องมือ:** unit test (Vitest) — อ่าน Expected / Received จากผลรัน test
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/validators/requestValidator.js:37` — เงื่อนไขใช้ `<=` (น้อยกว่าหรือเท่ากับ) แทนที่จะเป็น `<` ทำให้ค่า 10 พอดีถูกนับว่าไม่ผ่านด้วย
- **วิธีแก้:** เปลี่ยนเงื่อนไขเป็น `readText(input.details).length < MIN_DETAILS` ให้ตรงกับกฎ "อย่างน้อย 10 ตัวอักษร" (แก้โค้ดให้ตรงกับกฎ ไม่ใช่แก้ test ให้ตรงกับโค้ด)
- **test ที่กัน:** `api/tests/unit/requestValidator.test.js` → `'10 ตัวอักษร → ผ่าน (เท่ากับขอบ)'` และ `'9 ตัวอักษร → error (ต่ำกว่าขอบ 1)'`

## BUG #1 · ลบคำร้องแล้วเพิ่มใหม่ ได้ 500

- **อาการ:** ลบคำร้องรหัสกลาง ๆ (เช่น REQ-002) แล้วส่งคำร้องใหม่ → API ตอบ 500 Internal Server Error แทนที่จะเป็น 201
- **วิธีทำซ้ำ:** `curl -X DELETE localhost:3001/api/requests/REQ-002` แล้ว `curl -X POST localhost:3001/api/requests -d '{...ข้อมูลถูกต้อง}'` → ได้ 500 ทุกครั้ง
- **เครื่องมือ:** breakpoint ใน JavaScript Debug Terminal — ตั้งจุดหยุดใน `nextId()` แล้วดูค่าที่คำนวณได้ในแผง VARIABLES เห็นว่าได้รหัส REQ-005 ซ้ำกับที่มีอยู่แล้ว
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/services/requestService.js:101` (ฟังก์ชัน `nextId()`) — คำนวณรหัสถัดไปจาก `COUNT(*) + 1` พอลบ REQ-002 ไป จำนวนแถวเหลือ 4 → ได้รหัส REQ-005 ซ้ำกับคำร้องที่มีอยู่ → INSERT ชน PRIMARY KEY จึง 500
- **วิธีแก้:** เปลี่ยนมาใช้ `SELECT MAX(id)` แล้ว +1 จากตัวเลขสูงสุดของรหัสปัจจุบัน (REQ-005 → REQ-006) รหัสจะไม่ซ้ำไม่ว่าจะลบรายการไหนไป
- **test ที่กัน:** `api/tests/integration/requests.api.test.js` → `'ลบ REQ-002 แล้ว POST → 201 ได้รหัสถัดไปที่ไม่ซ้ำ (REQ-006 ไม่ใช่ REQ-005)'`

## BUG #2 · Dashboard แสดง "กำลังดำเนินการ 0"

- **อาการ:** การ์ด "กำลังดำเนินการ" บน Dashboard แสดง 0 ทั้งที่มีคำร้องสถานะ in-progress อยู่ 2 รายการ
- **วิธีทำซ้ำ:** เปิด Dashboard (`npm run dev --prefix frontend`) ดูการ์ดสรุป → แสดง "กำลังดำเนินการ 0" ทั้งที่ตารางมีรายการ in-progress
- **เครื่องมือ:** Chrome DevTools → แท็บ Network → ดู Response ของ `GET /api/requests` เห็น `"status": "in-progress"` (API ส่งค่าถูกต้อง) → ปัญหาจึงอยู่ฝั่ง frontend ไม่ใช่ API → ใช้ unit test จับต่อ
- **สาเหตุ (ไฟล์:บรรทัด):** `frontend/src/utils/requestSummary.js:12` — ฟังก์ชัน `summarizeRequests` นับด้วย `count('in progress')` (เว้นวรรค) แต่ API ส่งค่ามาเป็น `'in-progress'` (ยัติภังค์) เทียบกันแล้วไม่ตรงจึงนับได้ 0
- **วิธีแก้:** เปลี่ยนเป็น `count('in-progress')` ให้ตรงกับค่าที่ API ส่งมาจริง (แยกชั้นให้ชัด: API ถูกแล้ว จึงแก้ที่ frontend เท่านั้น)
- **test ที่กัน:** `frontend/src/utils/requestSummary.test.js` → `'นับตามค่า status จริงจาก API → inProgress = 2'`

## BUG #3 · เปลี่ยนสถานะคำร้องที่ไม่มีอยู่ ได้ 500

- **อาการ:** เปลี่ยนสถานะของคำร้องที่ไม่มีในระบบ (เช่น REQ-999) → API ตอบ 500 Internal Server Error แทนที่ควรจะเป็น 404 Not Found
- **วิธีทำซ้ำ:** `curl -X PUT localhost:3001/api/requests/REQ-999 -H "Content-Type: application/json" -d '{"status":"completed"}'` → ได้ 500 ทุกครั้ง
- **เครื่องมือ:** อ่าน stack trace จาก terminal ของ API — บรรทัดแรกบอกว่า `TypeError: Cannot read properties of null (reading 'id')` และบรรทัดแรกที่เป็นไฟล์ของเราชี้มาที่ `requestController.js:30` ใน `updateRequestStatus`
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/controllers/requestController.js:30` — `console.log` ใช้ `updated.id` ทันทีที่ `service.updateStatus()` คืนค่า ซึ่งคืน `null` เมื่อไม่พบคำร้อง (เช็ค `if (!updated)` ไว้หลัง log) → อ่าน property ของ null พังก่อนจะถึง 404
- **วิธีแก้:** ย้าย `console.log` ไปไว้หลังเช็ค `if (!updated) return 404` — จะ log เฉพาะเมื่อเปลี่ยนสถานะสำเร็จ
- **test ที่กัน:** `api/tests/integration/requests.api.test.js` → `'PUT /api/requests/REQ-999 → 404 ไม่ใช่ 500'`

# API Contract — Campus Service Request API

**เวอร์ชัน:** 2.0.0 · **Base URL:** `http://localhost:3001`
**รูปแบบข้อมูล:** JSON (`Content-Type: application/json`)

> **API Contract คืออะไร** — ข้อตกลงระหว่างคนทำ front-end กับคนทำ back-end
> ว่าจะคุยกันด้วย endpoint อะไร ส่งอะไรไป ได้อะไรกลับ
> มีไว้เพื่อให้สองฝั่ง**ทำงานคู่ขนานกันได้** โดยไม่ต้องรอกัน

---

## โครงสร้างข้อมูล Request

| field | ชนิด | คำอธิบาย | ตัวอย่าง |
|---|---|---|---|
| `id` | string | รหัสคำร้อง · ขึ้นต้นด้วย `REQ-` · เซิร์ฟเวอร์สร้างให้ | `"REQ-001"` |
| `requesterName` | string | ชื่อผู้แจ้ง · อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ประเภท · 1 ใน 4 ค่าที่กำหนด | `"แจ้งซ่อม"` |
| `location` | string | สถานที่ · ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | รายละเอียด · อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | `"pending"` · `"in-progress"` · `"completed"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** — `แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

## Endpoints

| Method | Endpoint | คำอธิบาย | Request body | สำเร็จ | ผิดพลาด |
|---|---|---|---|---|---|
| `GET` | `/api/requests` | ดูคำร้องทั้งหมด | — | `200` + array | — |
| `GET` | `/api/requests?status=` | กรองตามสถานะ | — | `200` + array | — |
| `GET` | `/api/requests/:id` | ดูคำร้องใบเดียว | — | `200` + object | `404` ไม่พบ |
| `POST` | `/api/requests` | สร้างคำร้องใหม่ | Request (ไม่ต้องมี `id`, `status`) | `201` + object ที่สร้าง | `400` ข้อมูลไม่ถูกต้อง |
| `PUT` | `/api/requests/:id` | เปลี่ยนสถานะ | `{ "status": "..." }` | `200` + object ที่แก้แล้ว | `400` สถานะผิด · `404` ไม่พบ |
| `DELETE` | `/api/requests/:id` | ลบคำร้อง | — | `204` ไม่มี body | `404` ไม่พบ |

## รูปแบบ Error

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

| Status | เมื่อไหร่ | ฝั่งไหนผิด |
|---|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้

## CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

**ถ้าเรียกจาก origin อื่น** เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response — จะเห็น error ใน Console ว่าถูกบล็อกโดย CORS policy

> ⚠ CORS เป็นกลไกของ **เบราว์เซอร์** เท่านั้น · Postman และ curl ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์

## Data Model (เพิ่มใน Week 10)

API เก็บข้อมูลในฐานข้อมูล SQLite (`api/data/campus.db`) แยกเป็น 2 ตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `name` | TEXT | NOT NULL |
| `department` | TEXT | NOT NULL |
| `email` | TEXT | NOT NULL UNIQUE |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | TEXT | PRIMARY KEY (รูปแบบ `REQ-NNN`) |
| `requester_id` | INTEGER | NOT NULL · FOREIGN KEY → `users(id)` |
| `request_type` | TEXT | NOT NULL · CHECK 4 ค่า |
| `location` · `details` | TEXT | NOT NULL |
| `priority` | TEXT | DEFAULT `'normal'` · CHECK |
| `status` | TEXT | DEFAULT `'pending'` · CHECK |
| `created_at` | TEXT | DEFAULT เวลาปัจจุบัน |

### ข้อสังเกตสำคัญ

**โครงสร้างในฐานข้อมูลไม่เหมือนรูปแบบที่ API ส่งออก**

- ฐานข้อมูลเก็บ `requester_id` (ตัวเลข) เพื่อไม่ให้ข้อมูลผู้ใช้ซ้ำ
- API คืน `requesterName` (ชื่อ) เพราะ frontend ต้องการแบบนั้น
- **ชั้น service เป็นตัวแปลงระหว่างสองรูปแบบด้วย `JOIN` และ `AS`**

ตอน POST — frontend ส่ง `requesterName` มา · service หา `id` ของชื่อนั้น ถ้ายังไม่มีก็สร้าง user ใหม่ให้ แล้วเก็บ `requester_id` ลงตาราง `requests`
