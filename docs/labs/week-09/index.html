## ตรวจ schema และ queries แยกจาก DB เดิม

ตรวจโดยรัน `schema.sql` ในฐานข้อมูล `:memory:` ใหม่ ไม่เขียนทับ `campus.db`:

```text
Schema seed: users=4, requests=8, foreignKeyViolations=0
Query 1: PASS; rows=8
Query 2: PASS; rows=3
Query 3: PASS; rows=3
Query 4: PASS; rows=2
Query 5: PASS; rows=8
Query 6: PASS; rows=4
Query 7: PASS; rows=4
Query 8: PASS; rows=3
NOT NULL: PASS (ปฏิเสธ users.name=NULL)
UNIQUE: PASS (ปฏิเสธ email ซ้ำ)
CHECK: PASS (ปฏิเสธ status='wrong-status')
PRIMARY KEY: PASS (ปฏิเสธ users.id=1 ซ้ำ)
FOREIGN KEY: PASS (ปฏิเสธ requester_id=999)
```

คำสั่ง Node ที่ใช้ตรวจจาก `lab09/source/` (ส่งโค้ดต่อไปนี้ให้ `node --disable-warning=ExperimentalWarning --input-type=module` ผ่าน stdin):

```js
import { DatabaseSync } from 'node:sqlite';
import { readFileSync } from 'node:fs';
const db = new DatabaseSync(':memory:');
db.exec(readFileSync('schema.sql', 'utf8'));
console.log('Schema seed:', JSON.stringify({
  users: db.prepare('SELECT COUNT(*) n FROM users').get().n,
  requests: db.prepare('SELECT COUNT(*) n FROM requests').get().n,
  foreignKeyViolations: db.prepare('PRAGMA foreign_key_check').all().length,
}));
const sql = readFileSync('queries.sql', 'utf8').replace(/--[^\n]*/g, '');
const queries = sql.split(';').map(s => s.trim()).filter(Boolean);
for (let i = 0; i < queries.length; i++) {
  console.log('Query ' + (i + 1) + ': PASS; rows=' + db.prepare(queries[i]).all().length);
}
const failures = [];
function reject(label, sql) {
  try {
    db.exec(sql);
    failures.push(label);
    console.log(label + ': FAIL (accepted invalid input)');
  } catch (error) {
    console.log(label + ': PASS (' + error.message + ')');
  }
}
reject('NOT NULL', "INSERT INTO users(name,department,email) VALUES(NULL,'test','not-null@test')");
reject('UNIQUE', "INSERT INTO users(name,department,email) VALUES('test','test','somchai@example.com')");
reject('CHECK', "UPDATE requests SET status='wrong-status' WHERE id='REQ-001'");
reject('PRIMARY KEY', "INSERT INTO users(id,name,department,email) VALUES(1,'test','test','pk@test')");
reject('FOREIGN KEY', "UPDATE requests SET requester_id=999 WHERE id='REQ-001'");
if (failures.length) process.exitCode = 1;
db.close();
```

ผลชุดนี้เป็น **pass** และ process exit code 0 แสดงว่า schema สามารถสร้างข้อมูลตั้งต้นครบและ SQL ทั้ง 8 คำสั่งรันได้ ส่วนความไม่ครบของ DB ที่ commit ไว้เดิมยังคงรายงานตาม checker ข้างต้น

-- ① คำร้องทั้งหมด เรียงตามรหัส
SELECT *
FROM requests
ORDER BY id;

-- ② คำร้องที่ยังไม่ได้ดำเนินการ (status = 'pending')
SELECT id, location, details
FROM requests
WHERE status = 'pending'
ORDER BY id;

-- ③ คำร้องเร่งด่วนที่ยังไม่เสร็จ — ใช้เงื่อนไข 2 ข้อพร้อมกัน
SELECT *
FROM requests
WHERE priority = 'urgent'
  AND status != 'completed'
ORDER BY id;

-- ④ ค้นคำร้องจากคำบางส่วนในรายละเอียด  (คำใบ้: LIKE)
SELECT *
FROM requests
WHERE details LIKE '%ไฟ%';

-- ⑤ คำร้องพร้อมชื่อผู้แจ้ง  ← ต้องใช้ JOIN เพราะชื่ออยู่คนละตาราง
SELECT
  r.id,
  u.name AS requesterName,
  r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id;

-- ⑥ คำร้องเฉพาะของภาควิชาหนึ่ง  (JOIN + WHERE)
SELECT
  r.id,
  u.name,
  u.department,
  r.details,
  r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
WHERE u.department = 'วิศวกรรมซอฟต์แวร์'
ORDER BY r.id;

-- ⑦ รายชื่อผู้แจ้งที่ไม่ซ้ำกัน  (คำใบ้: DISTINCT)
SELECT DISTINCT u.name
FROM users u
JOIN requests r ON r.requester_id = u.id
ORDER BY u.name;

-- ⑧ คำร้อง 3 รายการล่าสุด  (คำใบ้: ORDER BY + LIMIT)
SELECT *
FROM requests
ORDER BY created_at DESC
LIMIT 3;

# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวมและความสัมพันธ์ของข้อมูล

ระบบ Campus Service API แยกข้อมูลออกเป็น 2 ตารางหลัก ได้แก่ `users` และ `requests`

ความสัมพันธ์ของข้อมูลเป็นแบบ **One-to-Many (1:N)**

- ผู้ใช้ 1 คน (`users`) สามารถมีคำร้องได้หลายรายการ (`requests`)
- คำร้องแต่ละรายการจะอ้างอิงผู้สร้างคำร้องผ่าน `requester_id`
- `requester_id` เป็น Foreign Key ที่อ้างอิง `users.id`

```text
users
  |
  | 1
  |
  | N
  v
requests

users.id <---- requests.requester_id
```

การแยกข้อมูลลักษณะนี้ช่วยลดการเก็บข้อมูลซ้ำ และทำให้ข้อมูลผู้ใช้สามารถนำกลับมาใช้ร่วมกับคำร้องหลายรายการได้

---

## 2. เหตุผลที่แยกเป็น 2 ตาราง

หากเก็บข้อมูลผู้ใช้และข้อมูลคำร้องทั้งหมดไว้ในตารางเดียว จะเกิดปัญหาได้ เช่น

### 2.1 ข้อมูลซ้ำ (Duplicate Data)

หากผู้ใช้คนเดียวสร้างหลายคำร้อง ข้อมูล เช่น ชื่อ แผนก และอีเมล จะต้องถูกเก็บซ้ำในทุกคำร้อง ทำให้ฐานข้อมูลมีข้อมูลซ้ำโดยไม่จำเป็น

### 2.2 ปัญหาการแก้ไขข้อมูลไม่ครบ (Update Anomaly)

ถ้าผู้ใช้เปลี่ยนชื่อหรือเปลี่ยนแผนก หากข้อมูลถูกเก็บซ้ำหลายแถว จะต้องแก้ไขทุกแถว การแยก `users` ออกมาทำให้ข้อมูลผู้ใช้ถูกเก็บไว้เพียงจุดเดียว

### 2.3 ปัญหาการเพิ่มข้อมูล (Insert Anomaly)

การแยกตารางทำให้สามารถเพิ่มข้อมูลผู้ใช้ใน `users` ได้ก่อน แล้วจึงเพิ่มคำร้องใน `requests` ภายหลัง

### 2.4 ปัญหาการสะกดข้อมูลไม่ตรงกัน

เมื่อชื่อหรือแผนกถูกพิมพ์ซ้ำหลายครั้ง อาจเกิดการสะกดไม่เหมือนกัน การเก็บข้อมูลผู้ใช้ไว้ใน `users` ช่วยให้ข้อมูลหลักถูกจัดเก็บในจุดเดียว และ `requests` ใช้ `requester_id` สำหรับอ้างอิงแทนการคัดลอกข้อมูล

## 3. รายละเอียดของตาราง

### 3.1 ตาราง `users`

| Column | Type | Constraint | เหตุผล |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | ใช้ระบุผู้ใช้แต่ละคนแบบไม่ซ้ำกัน |
| `name` | TEXT | NOT NULL | ผู้ใช้ต้องมีชื่อ |
| `department` | TEXT | NOT NULL | ผู้ใช้ต้องมีหน่วยงาน/แผนก |
| `email` | TEXT | NOT NULL UNIQUE | ต้องมีอีเมลและไม่ควรมีผู้ใช้สองคนใช้อีเมลเดียวกัน |

### 3.2 ตาราง `requests`

| Column | Type | Constraint | เหตุผล |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | ใช้ระบุคำร้องแต่ละรายการ เช่น `REQ-001` |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY | ต้องระบุผู้สร้างคำร้องและต้องอ้างอิงผู้ใช้ที่มีอยู่จริง |
| `request_type` | TEXT | NOT NULL, CHECK | ต้องมีประเภทคำร้องและจำกัดค่าให้เป็นประเภทที่ระบบรองรับ |
| `location` | TEXT | NOT NULL | คำร้องต้องระบุสถานที่ |
| `details` | TEXT | NOT NULL | ต้องมีรายละเอียดของปัญหาหรือคำขอ |
| `priority` | TEXT | NOT NULL, DEFAULT, CHECK | กำหนดระดับความสำคัญเป็นค่าที่ระบบรองรับ |
| `status` | TEXT | NOT NULL, DEFAULT, CHECK | จำกัดสถานะให้เป็นค่าที่ระบบรองรับ |
| `created_at` | TEXT | NOT NULL, DEFAULT | บันทึกเวลาที่สร้างคำร้องโดยอัตโนมัติ |

ค่าที่กำหนดด้วย `CHECK` ได้แก่

```text
request_type:
- แจ้งซ่อม
- ขอใช้อุปกรณ์
- แจ้งปัญหา

priority:
- normal
- urgent

- pending
```

## 4. เหตุผลในการเลือกชนิดข้อมูลและ Constraint

### 4.1 ทำไม `users.id` และ `requests.id` จึงใช้ Type ต่างกัน?

`users.id` ใช้ `INTEGER` เพราะเป็นหมายเลขภายในฐานข้อมูลและใช้ `AUTOINCREMENT` เพื่อสร้างหมายเลขผู้ใช้ใหม่โดยอัตโนมัติ

ส่วน `requests.id` ใช้ `TEXT` เพราะระบบต้องการรหัสคำร้องที่อ่านง่ายและมีรูปแบบ เช่น `REQ-001`

ดังนั้นชนิดข้อมูลจึงแตกต่างกันตามลักษณะของรหัสที่ต้องการใช้งาน

### 4.2 ทำไมต้องมี CHECK Constraint ทั้งที่ API มี Validate อยู่แล้ว?

การตรวจสอบข้อมูลที่ API ช่วยป้องกันข้อมูลที่ไม่ถูกต้องจากผู้ใช้งาน API แต่ Database Constraint เป็นการป้องกันข้อมูลในระดับฐานข้อมูลอีกชั้นหนึ่ง

ตัวอย่างเช่น `status` สามารถกำหนดให้รับเฉพาะ `pending`, `in-progress` และ `completed`

ดังนั้นแม้ว่าจะมีโปรแกรมอื่นหรือคำสั่ง SQL พยายามบันทึกค่าอื่นลงฐานข้อมูล Database ก็ยังสามารถปฏิเสธข้อมูลที่ไม่ถูกต้องได้

จึงเป็นการป้องกันข้อมูลทั้งในระดับ Application และ Database

## 5. ตัวอย่าง JOIN และผลลัพธ์

สามารถใช้ `JOIN` เพื่อแสดงข้อมูลคำร้องพร้อมชื่อผู้ร้องได้ เช่น

```sql
SELECT
    r.id,
    u.name AS requester_name,
    u.department,
    r.request_type,
    r.location,
    r.details,
    r.priority,
    r.status,
    r.created_at
FROM requests r
JOIN users u ON r.requester_id = u.id
ORDER BY r.id;
```

ตัวอย่างผลลัพธ์:

| id | requester_name | department | request_type | location | priority | status |
|---|---|---|---|---|---|---|
| REQ-001 | สมชาย ใจดี | วิศวกรรมซอฟต์แวร์ | แจ้งซ่อม | ห้องปฏิบัติการ 101 | urgent | pending |
| REQ-002 | สุภาวดี รักเรียน | วิทยาการคอมพิวเตอร์ | ขอใช้อุปกรณ์ | ห้องเรียน 202 | normal | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | วิศวกรรมซอฟต์แวร์ | แจ้งปัญหา | ห้องสมุด | normal | completed |
| REQ-004 | กมลชนก สดใส | เทคโนโลยีสารสนเทศ | แจ้งซ่อม | ห้องปฏิบัติการ 302 | urgent | pending |
| REQ-005 | สมชาย ใจดี | วิศวกรรมซอฟต์แวร์ | ขอใช้อุปกรณ์ | ห้องประชุม | normal | completed |

> หมายเหตุ: ตารางด้านบนเป็นตัวอย่างผลลัพธ์ของ JOIN โดยข้อมูลจริงอาจมี REQ-006 ถึง REQ-008 เพิ่มเติมตาม seed data ของ `schema.sql`

## 6. สิ่งที่สังเกตได้เมื่อนำไปใช้กับ Week 10

การจัดเก็บข้อมูลแบบ Relational Database ทำให้ข้อมูลมีโครงสร้างชัดเจนและสามารถกำหนดความสัมพันธ์ระหว่างข้อมูลได้

ในระบบนี้ ตาราง `users` เก็บข้อมูลผู้ใช้ ส่วนตาราง `requests` เก็บข้อมูลคำร้องและใช้ `requester_id` เพื่อเชื่อมโยงกลับไปยังผู้ใช้

เมื่อทำงานร่วมกับ API ใน Week 10 สามารถใช้ SQL Query เพื่อดึงข้อมูลจากหลายตารางด้วย `JOIN` แล้วส่งผลลัพธ์กลับไปยัง Client ได้

ข้อสังเกตที่สำคัญคือ Database ช่วยดูแลเรื่องความถูกต้องของข้อมูล เช่น

- `PRIMARY KEY` ป้องกัน ID ซ้ำ
- `UNIQUE` ป้องกันอีเมลซ้ำ
- `NOT NULL` ป้องกันข้อมูลสำคัญหาย
- `FOREIGN KEY` ป้องกันการอ้างอิงผู้ใช้ที่ไม่มีอยู่จริง
- `CHECK` จำกัดค่าที่อนุญาตในบางฟิลด์

ดังนั้น Database จึงไม่ได้ทำหน้าที่เพียงเก็บข้อมูล แต่ยังช่วยรักษาความถูกต้องและความสอดคล้องของข้อมูลของระบบด้วย
