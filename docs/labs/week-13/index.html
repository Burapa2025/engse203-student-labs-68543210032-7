# LAB 13 — Pages verification

Verified on 2026-10-21 from branch `lab/week-13`, source commit `a66f5400b0844d921274a4018c76ffd848d32ebc`.

## Published result

This Pages entry presents authentication, authorization and security evidence for Campus Service (React + Express + SQLite). GitHub Pages hosts static files; running the interactive full-stack application also requires an Express API and a database.

## Verification environment

- Windows, Node.js `v24.18.0`, npm `11.16.0`.
- Source copied to a temporary validation directory, excluding `node_modules`, local `.env` files, database files, build output and coverage output.
- Dependencies installed from lockfiles with `npm ci --prefix .`, `npm ci --prefix api` and `npm ci --prefix frontend` (all exit 0).
- Tests used `DB_FILE=:memory:` and cleared `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`; no connection to a deployed database was used.
- The security checker uses development or disposable checker secrets. It verifies rejection of missing production secrets without reading local `.env` values.

## Commands and observed results

Run the following from `labs/week-13/source` after installing dependencies:

```powershell
$env:DB_FILE=':memory:'
$env:NODE_ENV='test'
Remove-Item Env:TURSO_DATABASE_URL,Env:TURSO_AUTH_TOKEN -ErrorAction SilentlyContinue
npm test
npm run check
npm run build --prefix frontend
```

| Command | Observed result |
| --- | --- |
| `npm test` | Exit 0. API: 4 test files, 68/68 tests passed. Frontend: 1 test file, 3/3 tests passed. |
| `npm run check` | Exit 0. In-class CP48–CP52: 23/23; challenge: 4/4; total: 27/27. |
| `npm run build --prefix frontend` | Exit 0. Vite 8.1.5 transformed 42 modules and generated `dist/index.html`, CSS and JavaScript assets. |

Security checks observed:

- Input length boundaries and rejection of request bodies larger than 10 KB.
- Salted scrypt password hashes, password verification and hashed staff seed records.
- Successful JWT login, token expiry information and uniform errors for incorrect credentials.
- Missing or forged token returns 401; a valid non-staff token returns 403; staff PUT/DELETE return 200/204.
- Public GET/POST remain available, and the earlier delete/create regression remains fixed.
- Production refuses to start without `JWT_SECRET`; production error responses omit stack traces.
- `X-Content-Type-Options: nosniff`; a sixth login attempt after five failures returns 429.
- The frontend API client attaches a stored Bearer token; `render.yaml` requests generated JWT secret configuration.

The integration suites exercise Express through Supertest using SQLite in memory. These results establish local automated checks; a deployed API and a browser login session were not part of this verification.

## API and backend requirements

- Use Node.js 22.13 or newer with the API dependencies from `api/package-lock.json`.
- A local API normally listens on `http://localhost:3001`; the frontend development server uses `http://localhost:5173`.
- The frontend reads `VITE_API_BASE_URL`; its default is `http://localhost:3001`. A public deployment needs the HTTPS URL of a running backend and a matching `CORS_ORIGIN` for the frontend origin.
- The API needs the SQLite schema at `api/data/schema.sql` and a writable database location selected by `DB_FILE`. `DB_FILE=:memory:` is suitable for disposable verification. Persistent deployment needs a durable database location or the separately configured remote database supported by the source.
- `NODE_ENV=production` requires `JWT_SECRET`. Supply a deployment secret through the backend environment. `/api/auth/login` issues tokens; staff roles are required for PUT and DELETE on `/api/requests/:id`.
- `/api/health` reports service and database connectivity. CRUD operations use `/api/requests`; user endpoints use `/api/users`.
- For production on one backend origin, build the frontend with `VITE_API_BASE_URL` set to an empty string so it requests `/api/...`, then run the API in production. Hosting a static build on Pages alone does not supply these endpoints.
- The supplied frontend includes token storage and Bearer forwarding. The source describes a complete login screen as later Term Project work, so this report does not claim a finished browser sign-in flow.

## BUG #0 · ค่าขอบรายละเอียด 10 ตัวอักษร (test เจอ — ไม่มีผู้ใช้แจ้ง)

- **อาการ:** ส่งรายละเอียด 10 ตัวอักษรพอดี ถูกปฏิเสธ ทั้งที่ข้อความบอกว่า "อย่างน้อย 10"
- **วิธีทำซ้ำ:** unit test `validateRequestInput({ ...valid, details: '1234567890' })`
- **เครื่องมือ:** unit test ค่าขอบ (TC-03) — fail ทันทีที่เขียน
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/validators/requestValidator.js` เงื่อนไข `length <= MIN_DETAILS` ทำให้ 10 ตัวถูกนับว่าไม่ผ่าน
- **วิธีแก้:** เปลี่ยนเป็น `length < MIN_DETAILS`
- **test ที่กัน:** `tests/unit/requestValidator.test.js` → "10 ตัวอักษร → ผ่าน (ตรงขอบพอดี)"

## BUG #1 · ลบคำร้องแล้วเพิ่มใหม่ ได้ 500

- **อาการ:** หลังลบคำร้องรายการกลาง การสร้างคำร้องใหม่ได้ 500
- **วิธีทำซ้ำ:** `DELETE /api/requests/REQ-002` แล้ว `POST /api/requests` → 500
- **เครื่องมือ:** อ่าน log ใน terminal (`UNIQUE constraint failed: requests.id`) → วาง breakpoint ใน `nextId()` ด้วย JavaScript Debug Terminal เห็นว่าได้ `REQ-005` ซึ่งมีอยู่แล้ว
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/services/requestService.js` ฟังก์ชัน `nextId()` คำนวณรหัสจาก `COUNT(*) + 1` — เมื่อลบรายการกลาง จำนวนลดลง รหัสที่ได้จึงชนกับรหัสที่ยังอยู่
- **วิธีแก้:** หารหัสล่าสุด (`ORDER BY id DESC LIMIT 1`) แล้วบวก 1
- **test ที่กัน:** `tests/integration/requests.api.test.js` → "ลบรายการกลาง แล้วเพิ่มใหม่ → 201 และรหัสไม่ซ้ำของเดิม"

## BUG #2 · Dashboard แสดง "กำลังดำเนินการ 0"

- **อาการ:** การ์ดสรุปบอกว่ากำลังดำเนินการ 0 แต่ในรายการมีคำร้อง in-progress
- **วิธีทำซ้ำ:** เปิด Dashboard ด้วยข้อมูลตั้งต้น (REQ-002 เป็น in-progress)
- **เครื่องมือ:** DevTools → Network → `GET /api/requests` ส่ง `"status": "in-progress"` ถูกต้อง → ปัญหาอยู่ฝั่ง frontend → วาง breakpoint ใน `summarizeRequests` (DevTools → Sources)
- **สาเหตุ (ไฟล์:บรรทัด):** `frontend/src/utils/requestSummary.js` นับด้วย `'in progress'` (ช่องว่าง) แทน `'in-progress'` (ขีด) จึงไม่ตรงกับค่าที่ API ส่งมา
- **วิธีแก้:** ใช้ `'in-progress'` ให้ตรงกับ API
- **test ที่กัน:** `frontend/src/utils/requestSummary.test.js` → "นับครบทุกสถานะ"

## BUG #3 · เปลี่ยนสถานะคำร้องที่ไม่มีอยู่ ได้ 500

- **อาการ:** `PUT /api/requests/REQ-999` ได้ 500 แทน 404
- **วิธีทำซ้ำ:** `curl -X PUT localhost:3001/api/requests/REQ-999 -H "Content-Type: application/json" -d '{"status":"completed"}'`
- **เครื่องมือ:** อ่าน stack trace ใน terminal — บรรทัดแรกบอก `TypeError: Cannot read properties of null (reading 'id')` บรรทัดถัดไปบอกไฟล์และบรรทัดใน controller
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/controllers/requestController.js` ใน `updateRequestStatus` มีบรรทัด log `updated.id` อยู่**ก่อน**การตรวจ `if (!updated)` — เมื่อไม่พบคำร้อง `updated` เป็น null จึงพัง
- **วิธีแก้:** ย้าย log ไปไว้หลังการตรวจ null
- **test ที่กัน:** `tests/integration/requests.api.test.js` → "คำร้องที่ไม่มีอยู่ → 404 (ไม่ใช่ 500)"

# API Contract — Campus Service Request API

**เวอร์ชัน:** 2.0.0 · **Base URL:** `http://localhost:3001`
**รูปแบบข้อมูล:** JSON (`Content-Type: application/json`)

> **API Contract คืออะไร** — ข้อตกลงระหว่างคนทำ front-end กับคนทำ back-end
> ว่าจะคุยกันด้วย endpoint อะไร ส่งอะไรไป ได้อะไรกลับ
> มีไว้เพื่อให้สองฝั่ง**ทำงานคู่ขนานกันได้** โดยไม่ต้องรอกัน

## โครงสร้างข้อมูล Request

| field | ชนิด | คำอธิบาย | ตัวอย่าง |
|---|---|---|---|
| `id` | string | รหัสคำร้อง · ขึ้นต้นด้วย `REQ-` · เซิร์ฟเวอร์สร้างให้ | `"REQ-001"` |
| `requesterName` | string | ชื่อผู้แจ้ง · อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ประเภท · 1 ใน 4 ค่าที่กำหนด | `"แจ้งซ่อม"` |
| `location` | string | สถานที่ · ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | รายละเอียด · อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | `"pending"` · `"in-progress"` · `"completed"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** — `แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

## รูปแบบ Error

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

| Status | เมื่อไหร่ | ฝั่งไหนผิด |
|---|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้

## CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

**ถ้าเรียกจาก origin อื่น** เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response — จะเห็น error ใน Console ว่าถูกบล็อกโดย CORS policy

> ⚠ CORS เป็นกลไกของ **เบราว์เซอร์** เท่านั้น · Postman และ curl ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์

## Data Model (เพิ่มใน Week 10)

API เก็บข้อมูลในฐานข้อมูล SQLite (`api/data/campus.db`) แยกเป็น 2 ตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `name` | TEXT | NOT NULL |
| `department` | TEXT | NOT NULL |
| `email` | TEXT | NOT NULL UNIQUE |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | TEXT | PRIMARY KEY (รูปแบบ `REQ-NNN`) |
| `requester_id` | INTEGER | NOT NULL · FOREIGN KEY → `users(id)` |
| `request_type` | TEXT | NOT NULL · CHECK 4 ค่า |
| `location` · `details` | TEXT | NOT NULL |
| `priority` | TEXT | DEFAULT `'normal'` · CHECK |
| `status` | TEXT | DEFAULT `'pending'` · CHECK |
| `created_at` | TEXT | DEFAULT เวลาปัจจุบัน |

### ข้อสังเกตสำคัญ

**โครงสร้างในฐานข้อมูลไม่เหมือนรูปแบบที่ API ส่งออก**

- ฐานข้อมูลเก็บ `requester_id` (ตัวเลข) เพื่อไม่ให้ข้อมูลผู้ใช้ซ้ำ
- API คืน `requesterName` (ชื่อ) เพราะ frontend ต้องการแบบนั้น
- **ชั้น service เป็นตัวแปลงระหว่างสองรูปแบบด้วย `JOIN` และ `AS`**

ตอน POST — frontend ส่ง `requesterName` มา · service หา `id` ของชื่อนั้น ถ้ายังไม่มีก็สร้าง user ใหม่ให้ แล้วเก็บ `requester_id` ลงตาราง `requests`

## สถาปัตยกรรม 3 ชั้น

```
┌─────────────┐   HTTP    ┌──────────────┐   SQL    ┌───────────┐
│  React      │ ────────► │  Express API │ ───────► │  SQLite   │
│  (frontend) │ ◄──────── │  (api)       │ ◄─────── │  campus.db│
└─────────────┘   JSON    └──────────────┘   rows   └───────────┘
   พอร์ต 5173              พอร์ต 3001              ไฟล์ในเครื่อง
```

| ชั้น | หน้าที่ | โฟลเดอร์ |

## วิธีรัน (production)

```bash
# build แบบเดียวกับ cloud (script อยู่ใน package.json ระดับบนสุด)
NODE_ENV=production npm install
NODE_ENV=production npm run build

# start — เสิร์ฟทั้งหน้าเว็บและ API จากพอร์ตเดียว (สัปดาห์ 13: production ต้องตั้ง JWT_SECRET ไม่งั้นไม่ยอม start)
NODE_ENV=production JWT_SECRET=<ค่าสุ่ม> PORT=10000 npm start
# เปิด http://localhost:10000
```

| ไฟล์ | ทำให้ production ทำงานอย่างไร |
|---|---|
| `frontend/.env.production` | `VITE_API_BASE_URL=` ว่าง → frontend เรียก `/api/...` บนโดเมนเดียวกัน |
| `api/src/app.js` | production เสิร์ฟ `frontend/dist` · path ที่ไม่ใช่ `/api` ได้ index.html |
| `package.json` | `build` ใช้ `--include=dev` เพราะ cloud ตั้ง NODE_ENV=production ตั้งแต่ build |

## ความปลอดภัย (สัปดาห์ 13)

| เรื่อง | ไฟล์ |
|---|---|
| validation เข้มขึ้น (ชนิดข้อมูล · ความยาวสูงสุด · body ≤ 10kb) | `api/src/validators/requestValidator.js` · `api/src/app.js` |

| secret มาจาก env · production ไม่มี secret = ไม่ start | `api/src/config.js` · `api/.env.example` |
